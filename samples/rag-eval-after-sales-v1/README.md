# 售后 RAG 评测练习资料 v1

全部品牌、设备、参数、工单和规则均为虚构，仅供软件评测练习，不适用于真实设备。资料快照日期：2026-10-01。

## 场景

虚构品牌「澄印」销售 NX100 和 NX200 两款标签打印机。售后助手根据用户问题、已知设备信息和知识库，给出有来源的建议；必要时追问或转人工。

本轮只评测：给定设备信息 → 检索知识 → 生成建议。查询设备、追问的多轮执行、创建工单工具的成功率留到后续智能体评测。

## 文件用途

- `corpus/`：10 份可进入检索索引的原始资料，包含手册、故障指南、服务规则、更新公告和历史工单。保留标题、文档 ID、章节 ID 和适用范围。
- `fixtures/devices.json`：模拟设备查询工具的返回数据。由应用按 device_id 读取并传入上下文，不作为知识文档进行语义检索。
- `eval/dev_cases.jsonl`：12 道开发用评测题及人工编写的判定要求。不得进入检索索引，也不得把参考要求传给被测模型。

## 资料中的差异

NX100 的 E17 表示上盖未闭合，NX200 的 E17 表示打印头过热。NX100 的校准流程在固件 1.5.0 起改变。历史工单中既有已解决案例，也有未经验证的用户猜测。旧版指南真实地保留在语料中，但带有明确的替代关系。

## 第一轮怎么用

1. 先阅读一个案例对应的原始资料，手工判断回答需要哪些证据。
2. 仅将 corpus 中的文件建立索引，保留 `doc_id`、`section_id`、型号、版本和文档状态等元数据。
3. 对每道题传入 question，以及 device_id 对应的设备信息（若为空，则没有设备信息）。不要传入其他评测字段。
4. 保存每道题的检索片段、来源章节、最终回答、配置版本和耗时。
5. 用 required_evidence_groups 检查证据覆盖，用 must_include 和 must_not_include 人工检查回答，并检查引用是否真的支持对应主张。

每个 required_evidence_groups 内的章节是可替代证据；组与组之间都需要覆盖。可先用“已命中的证据组数 / 总证据组数”作为教学用覆盖率。这是本资料的自定义指标，不等同于标准文档 Recall@k。切分后必须保留原章节 ID；不能用全文文档命中代替必要章节命中。

## 评测边界

这 12 道题全部是可用于调试的开发题，不是隐藏测试集。critical 表示练习中的高风险要求；regular 表示普通要求，不表示问题在真实业务中的出现频率。不能把各题等权平均分直接当成生产表现。

must_include 是语义要求，不要求逐字匹配；must_not_include 需要结合否定语境判断。例如“不要使用清洗剂”不能因为包含“清洗剂”就判错。暂时不要用关键词包含规则冒充答案质量评测。

这是一份人工构造的教学数据集，不能证明生产可用。后续需要引入真实用户问题、人工复核、未参与调优的测试集，以及对失败类型的统计。这里尚未接入或运行 RAG，也没有模型评分结果。
